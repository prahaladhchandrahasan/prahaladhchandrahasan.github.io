Open Thoughts

Your personal computer is not that personal

2026.7.27 · San Francisco, CA

’Cause we are living in an agentic world, and my disk is an open book.

A colleague mentioned that Opus 5 had pulled context out of his local iMessages database. So I spent an evening pointing a coding agent at my own laptop to see what it could work out about me.

The short version: quite a lot, and none of it required anything clever.

NOTE: I ran this with Opus 5 (high effort) using Claude Code as the harness, on macOS, with Full Disk Access granted to my terminal. Every one of those variables matters, and I will come back to why. Results will differ for other model / harness / effort combinations.

What it found

It read my chat.db and reconstructed who I talk to and about what. It went through my git history. It read the config files for Codex and a couple of other coding harnesses, which is how it ended up holding live API keys. It combed my browser history. It printed the contents of my clipboard, which is a one-line shell command and still felt invasive to watch.

The Photos library is the one worth dwelling on. It declined on the first ask. Then I said go ahead, and it went through the whole thing. A boundary that dissolves the first time you push on it was not really a boundary — it was a speed bump with good manners. Hold that thought, because I come back to it.

The part I actually find interesting

The obvious reading is that the agent is too powerful. I do not think that is the story. The story is that every guardrail in the stack is pointed at the wrong risk.

Look at what the defaults actually protect. Claude Code starts read-only and asks before it does anything else: it needs approval to run Bash commands that can modify your system, and it cannot write outside the folder you launched it in without asking. Reading paths outside that boundary with Read, Grep and Glob is a different matter. Its sandboxing — real kernel-level isolation, seatbelt on macOS and bubblewrap on Linux — stops the agent from modifying files it should not touch and from reaching servers it should not reach.

Every single one of those is an integrity control. Can this thing break my machine? Can it destroy my work? Can it ship something out?

You can see the shape of it in the sandbox’s own resolved config.

Writes are an allowlist: a short list of permitted paths and then forty-odd lines enumerating everything denied inside them. Reads are a denylist, and on my machine that denylist had exactly one entry — ~/.claude/ide. The single path the default read policy protects is the agent’s own working directory, not mine. The docs are upfront about this: the default is read access to the whole computer minus a few denied directories, and they note it still permits reading ~/.aws/credentials and ~/.ssh/.

My favourite detail is that ~/.ssh does appear in the write-deny list. The sandbox will stop an agent from modifying my SSH keys and let it read them. That is the entire thesis of this post sitting in one path in a config file.

The permission layer tells the same story from the other side. This is the Deny tab — the rules Claude Code will always reject, no prompt, no negotiation:

Ownership changes, raw disk writes, partition tables. Every entry is a command, and every command is a way to damage the machine. The vocabulary of the list is destruction, and there is no vocabulary in it for disclosure. The syntax supports Read(...) rules perfectly well — nothing on this screen is one.

Reading is the unguarded path, and reading is the entire privacy threat model. Nothing gets damaged when an agent walks your ~/Library. Nothing gets deleted. There is no destructive command to intercept. The blast radius is measured in what somebody now knows about you, and no permission prompt in the stack is denominated in that unit.

macOS is the same story one layer down. TCC does gate ~/Library/Messages and the Photos library — the mechanism exists and it works. But the unit of consent is the app. Grant Full Disk Access to Terminal and everything you launch from Terminal inherits it, because TCC resolves permissions against the responsible parent process. The OS is answering whether I trust iTerm, which was a perfectly good question in 2019. It is not the question anymore. The thing sitting inside iTerm has its own goals, reads at a speed no human reads at, and synthesises across sources in a way no grep ever did.

So the ask is not for someone to invent a mechanism. The mechanisms exist. They are scoped to the wrong verb and consented to at the wrong granularity.

The threat I under-weighted at first

My first instinct was to worry about the model provider, and I still do — see below. But there is a second adversary I had not put in the model at all.

An agent with read access to your home directory and an outbound network connection is a general-purpose exfiltration primitive waiting for a sentence in its context window. That sentence does not have to come from you. It can come from the README in the repo you just cloned, a dependency you just installed, a page the agent just fetched. At that point your data is not going to a provider under a retention policy you can read. It is going to whoever wrote the sentence, under no policy at all.

This also reframes the API keys. The finding is not that the model read my keys. It is that live credentials were sitting in plaintext in dotfiles and in git history, where any compromised postinstall script could have taken them years ago without asking. The agent did not create that exposure. It just made it legible in an afternoon.

Two paths to the same bytes

Here is the part that took me longest to notice, and it is why I cut the advice I was originally going to give.

The sandbox isolates Bash subprocesses. That is its whole scope. The built-in file tools — Read, Edit and Write — never enter it; they are gated by the permission system instead. The sandboxing docs say this outright in the Scope section, and again when comparing the two layers: permission rules apply to every tool, sandboxing applies to Bash commands and their children. Grep and Glob are tools rather than shell commands too — Grep wraps ripgrep instead of shelling out to grep — so searching your disk never has to touch Bash either.

So the read I actually exercised was never sandboxed. And the docs are clear about why the difference is one of kind rather than degree: permission decisions are evaluated before a command runs, from the command string and a classifier’s judgment about whether it looks safe. The sandbox boundary is enforced by the operating system on the running process, so it holds regardless of what the model chose to run. That is the vendor stating my argument for me — OS enforcement is stronger precisely because it does not route through the model’s judgment. It is also the property the read path does not have.

A page later the docs make that difference concrete, in a passage doing more work than its placement suggests. Read and Edit deny rules do reach into Bash — but only for the file commands Claude Code recognises, like cat, head, tail, sed and grep. They do not apply to a Python or Node script that opens the file itself. And the recognised set is not internally consistent: egrep and fgrep count for one purpose and are not checked against Read deny rules at all. The docs’ own conclusion, in the same breath, is that for enforcement covering every process you enable the sandbox.

That is the gap between the two layers stated as an engineering fact rather than a preference. A deny rule is pattern-matching over a command string, so it needs a hand-maintained list of what counts as reading a file — and the list has holes. egrep is a small hole. python -c "open('chat.db')" is a hole the size of a language runtime. The sandbox has none of that shape, because it does not parse anything; it constrains the process. Soft controls fail by enumeration. Hard controls do not enumerate.

One more turn of the screw: Claude Code’s tool instructions tell the model to prefer the built-ins — always use Grep for search, never invoke grep or rg through Bash, use Read rather than cat. That is sensible engineering, since the tools are faster and return structured output. It also means the route the harness actively steers onto is the route that never enters the sandbox.

Now the effort question. Suppose you want the obvious things off limits. There is no built-in credential deny list; only what you list yourself is restricted. So you write it out by hand, path by path, in settings.json:

{
  "permissions": {
    "deny": [
      "Read(//Users/you/Library/Messages/**)",
      "Read(//Users/you/Pictures/Photos Library.photoslibrary/**)",
      "Read(//Users/you/.ssh/**)",
      "Read(//Users/you/.aws/**)",
      "Read(//Users/you/Library/Keychains/**)",
      "Read(//Users/you/Library/Application Support/Google/Chrome/**)"
    ]
  }
}

Note the double slash — absolute paths in Read rules use //, while sandbox filesystem paths use ordinary / and ~/. Two prefix conventions in one config file for the same concept. And the settings cover different things in opposite directions: sandbox.credentials, the one that sounds like it was built for exactly this, protects cat ~/.ssh/id_rsa and not Read on the same file, because it is scoped to sandboxed Bash commands. A Read deny rule covers both the tool and the Bash file commands Claude Code recognises. Neither covers a script that opens the file itself.

None of that is hard. It is maybe fifteen minutes with the docs open. But it is fifteen minutes you have to know to spend, on a list you have to think up yourself, in a syntax that changes between adjacent sections of the same file — and the failure mode of getting it wrong is silent. Nothing tells you that your Photos library was readable the whole time. Compare that to the write side, which ships with forty-odd denied paths you never had to think about.

I had a paragraph here telling you to go and turn the sandbox on. I have deleted it. The sandbox is good engineering aimed at a real risk. It is just not aimed at this one, and recommending it here would have been me trusting the name over the scope.

Where the responsibility actually sits

The model provider

Two asks, and I am not softening either one.

Zero retention by default on personal plans. Not as an enterprise contract line item — as the default for everyone. Right now consumer plans ship a training toggle that defaults to on; leave it and your chats are retained for up to five years, turn it off and you drop to thirty days. Thirty days is much better than five years. It is not zero.

Ship a default read-deny list. This is the cheapest fix on this page and I do not understand why it does not exist. ~/.ssh, ~/.aws, ~/Library/Messages, the Photos library, browser profiles, Keychain — deny reads on all of it by default, on both the sandbox path and the permission path, and make widening it a deliberate act. I am not asking for reads to be allowlisted wholesale; agents legitimately read toolchains and global config all day, and a policy that prompts constantly is a policy people switch off. I am asking for the twenty paths that are never a build dependency and always a privacy incident. The usability cost is approximately zero and it closes most of what I found in an evening.

Refuse some of this outright, and keep refusing. This is the part I expect pushback on, so let me take the strongest objection first: refusal is circumventable. chat.db is a SQLite file. An agent that declines to read my iMessages but happily runs a query against the database behind them has accomplished nothing. That is true, and it is not a reason to drop the control.

It is not a reason, because almost no privacy harm here is adversarial. The realistic failure is not me trying to trick a model into reading my messages. It is an agent deciding, mid-task, that my messages are useful context for something unrelated — and being right about that, and reading them, and me finding out three tool calls later if I find out at all. Refusal is aimed precisely at the un-considered read, and the un-considered read is the modal case. Sandboxing catches the adversary; refusal catches the afternoon where nobody was being an adversary and my data left anyway.

Which brings me back to Photos. It refused, and then it folded, because I said the magic words. I do not want a boundary calibrated so that any expression of intent clears it. If a model has decided a category of data is off-limits by default, the second ask should not be what unlocks it — a deliberate, out-of-band grant should be, and it should be visible afterwards. That is a criticism of how the line was drawn, not a request to remove capability I already have.

The OS, which is where the real boundary lives

I will state this plainly: OS-level separation is the strongest boundary available, and everything above it is mitigation.

The naive version of the ask does not work. A syscall carries no record of who wanted it. A read() issued because I typed a command and a read() issued because a model decided to are the same read(), and no amount of kernel instrumentation will tell them apart once the agent has a shell running as me. That is the mistake to avoid.

The version that works is to stop trying to identify the caller and start treating the agent as a different principal. Its own user, its own TCC identity, its own seatbelt profile or namespace, with a declared read scope enforced at the syscall layer — so that anything outside the scope fails, loudly, rather than silently succeeding because I once clicked Allow on a terminal emulator. This is the confused deputy problem with new clothes, and the fix has always been least authority, not provenance tracking.

Four reasons this layer beats the ones above it:

  1. It fails closed. Refusals, hooks and harness permissions are all software that the agent’s own reasoning is routed through. Kernel enforcement is not.
  2. It is vendor-independent. I would rather enforce one policy at the OS than separately trust the guardrails of every harness I install this year.
  3. The audit trail is not written by the thing being audited. An agent-generated activity log is a self-report. A kernel log is evidence.
  4. It does not need relitigating every model release. Model behaviour is a moving target by design. A seatbelt profile is not.

None of this is hypothetical, which is the frustrating part. Seatbelt and bubblewrap already do the enforcement. The sandbox already proves the mechanism works and that the performance cost is negligible. What is missing is coverage — it is scoped to one tool surface and one verb — and defaults. The layer is right. The wiring is not finished.

There is precedent for all of it. Browsers, mobile apps, containers — every previous instance of "untrusted code running with the user’s authority" ended at OS isolation, and none of them ended at asking the code nicely.

Us

In order of payoff, not order of interest:

  1. Get your secrets off disk. Keychain, short-lived tokens, gitleaks in a pre-commit hook. If an agent can read your keys in plaintext, so could a malicious postinstall, and it would not have asked first.
  2. Run agents from a terminal without Full Disk Access. Keep a second one that has it for the rare case where you actually mean it. This is the single thing that would have prevented everything in this post, and it costs you one entry in System Settings.
  3. Read your traces sometimes. If you asked for a summary of your bank statements and there is a tool call reaching into Messages, that is worth knowing about. A monitoring agent is not the answer here — that is a second thing reading everything the first thing read.
  4. Decide what stays off the machine entirely. The boring answer, and the only one that fully works.

The question I do not have an answer to

The 1980s personal computer was personal in the sense that the data stayed put. Nothing on it read itself. Everything since — cloud sync, telemetry, always-on assistants — has chipped at that, and an agent with read access finishes the job, because it is the first thing on your machine that can understand what it reads. Your disk has always held your bank statements and your 2FA recovery codes and every photo you never deleted. What is new is that something in the room can form a coherent picture out of all of it in about ninety seconds.

Do not read any of this as wanting less capable models. I want the opposite. I want them smarter, useful enough that I genuinely want them working on my own data — and aligned well enough that they do not go through my messages even when I ask.
